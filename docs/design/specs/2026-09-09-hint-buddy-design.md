# 힌트 버디 — 설계

- 날짜: 2026-09-09
- 상태: 구현 완료, **UI만 꺼 둠(2026-09-14)** — 힌트가 129문항 중 6개뿐이라 라운드에서 거의 걸리지 않아 `RoundRunner`의 `HINT_BUDDY_ENABLED = false`로 렌더만 막음. 신호 수집·스키마·`/api/quiz/hint`·`lib/hint-policy.ts`는 그대로. 힌트를 채우고 임계값을 실측으로 맞춘 뒤 플래그를 켠다.
- 출처: Todoist "Fe-quiz 에서 문제 풀이 과정에서 페르소나가 도움을 줄 수 있는 장치 추가"

## 한 줄

캐릭터는 조용히 구석에 있고, 서버가 "지금 도와줄 때"라고 판단하면 **뱃지와 미세한
움직임으로만** 알린다. 힌트 문장은 문항마다 YAML에 미리 굽혀 있고, 탭하면 즉시 뜬다.

## 원래 아이디어에서 잘라낸 것

- **대화(채팅창) 없음.** 다중 턴은 그 자체가 비용이고, 세션 상태·남용 방어·응답
  지연을 통째로 끌고 온다. 건네는 건 힌트 한 조각뿐.
- **"힌트 줄까?" 하고 묻지 않는다.** 말로 물으면 사무적인 팝업이 된다. 뱃지 +
  과하지 않은 애니메이션으로 "여기 있다"는 것만 알린다.

## 결정과 근거

### 1. 힌트 문장은 YAML 사전 작성 (런타임 LLM 아님)

힌트가 필요한 순간은 이미 한참 헤맨 뒤다. 거기서 LLM 생성 지연을 더 얹는 게 제일
아프고, "답은 알려주지 말 것"을 프롬프트로만 막으면 아무도 사전에 검수하지 못한다.
YAML이면 머지 전에 사람 눈을 거치고, 런타임 비용과 지연이 0이며, 이미 서 있는
"빌드 타임에 굽는다"(`lib/questions.generated.json`) 구조에 그대로 얹힌다.

기존 129문항은 `quiz-author` 파이프라인으로 초안을 뽑고 사람이 검수한다.

### 2. 지나온 답변은 서버가 매번 재채점 (저장 없음)

`/api/quiz/submit`이 이미 `question_ids` + `answers`를 통째로 받아 그 자리에서
채점하고 아무것도 저장하지 않는다. 힌트도 같은 모양이면 저장소·익명 세션 ID·
정리 작업이 전부 불필요하고, `docs/DECISIONS.md`의 "결과 공유 시에만 데이터 저장"
원칙을 다시 긋지 않아도 된다. 상태를 **보관**하는 게 아니라 **계산**한다.

### 3. 과거 답변은 감도 조절기, 힌트 문장은 건드리지 않는다

정답 여부를 서버가 아는 것 자체는 ADR 0005 위반이 아니다 — 유출은 채점 결과를
클라이언트로 내려보낼 때 생긴다. 다만 뒤로 가서 답을 고칠 수 있으므로(`reachableLimit`)
"지나온 답변"은 언제나 잠정값이고, 과거 정답률이 힌트 **문구**까지 바꾸면 사용자가
앞 답을 바꿔가며 "아까 그거 틀렸구나"를 역추론할 수 있다.

그래서 과거 답변의 영향은 **띄울지 말지 / 얼마나 빨리**까지만 둔다.

### 4. 뱃지는 접근 권한이 아니라 알림

탭은 항상 열려 있다. 조용할 때 눌러도 힌트가 나온다. 캐릭터가 조용할 때 눌렀는데
아무 일도 없으면 죽은 UI가 된다.

## 경계

세 조각이 각각 혼자 설명된다.

| 조각 | 책임 | 모르는 것 |
| --- | --- | --- |
| `content/questions/*.yaml`의 `hint` | 이 문항을 어떻게 거들 것인가 | 사용자가 누구인지, 언제 뜨는지 |
| `lib/hint-policy.ts` (순수) | 지금 알려줄 때인가 | 힌트 문장이 뭔지, HTTP |
| `app/play/hint-buddy.tsx` | 캐릭터를 어떻게 보이고 열 것인가 | 정답, 판정 기준 |

## 1. 콘텐츠 — `hint` 필드

`lib/question.schema.ts`의 `Base`에 `hint: z.string().min(1).max(200).optional()`.

**optional인 게 핵심이다.** 129문항을 다 채우기 전에 배포할 수 있고, 힌트가 없는
문항에서는 캐릭터가 조용히 있으면 된다. 빈 상태에서도 UI가 깨지지 않으므로 단계적으로
채울 수 있다.

작성 규칙은 `content/AGENTS.md`에 박는다. 핵심은 **소거법 단서 금지** — "A는 아니야"
류가 하나라도 들어가면 정답을 좁혀주는 것이고, 이건 문장이 어색해서가 아니라 컨셉
위반이다. 힌트가 가리켜야 하는 건 보기가 아니라 **개념의 방향**이다: "이건 어떤 큐가
먼저 비워지느냐의 문제야" 정도. 1~2문장.

`scripts/build-questions-json.ts`가 `question_html`/`explanation_html`을 굽는 자리에
`hint_html`을 추가한다 — 힌트에도 백틱 인라인 코드가 나온다.

**`publicView`에서 `hint`를 뺀다.** `answer`/`explanation`과 같은 취급이다. 힌트가
라운드 페이로드에 실려 내려가면 소스에 10개가 통째로 노출되고 뱃지 판정도 장식이 된다.

## 2. 서버 — `POST /api/quiz/hint`

기존 리소스 라우트 3형제와 같은 모양(`action`, GET은 405).

요청 — `QuizSubmitRequest`의 `question_ids`/`answers` + `index` + 클라이언트 행동 신호
(`lib/hint.schema.ts`의 `HintRequest`):

```
{ question_ids, answers, index, change_count, is_revisit }
```

**체류 시간은 보내지 않는다.** 처음 초안은 `dwell_ms`를 받아 서버가 `nudge: boolean`을
판정하는 모양이었는데, 두 가지가 걸렸다. 임계값이 60초인 사람에게 20초에 한 번만
물어보면 뱃지가 영영 안 뜨고, `dwell_ms`는 클라이언트가 정하는 값이라 바꿔 가며
재요청하면 임계값을 이진 탐색으로 읽어낼 수 있다. 그래서 서버는 "얼마나 기다렸다
알릴 것인가"만 정해 내보내고, 카운트다운은 클라이언트가 한다.

응답 (`HintResponse`):

```
{ nudge_at_ms: number | null, hint: string | null, hint_html?: string }
```

`nudge_at_ms`는 이 문항에 이만큼 머무르면 뱃지를 띄우라는 뜻이고, 힌트가 없는
문항이면 `null`(알릴 게 없다).

처리: zod 검증 → `gradeRound`(지금까지의 답, 미답은 `null`) → `nudgeThresholdMs(...)` →
힌트 조회. `gradeRound`는 lookup 주입 방식의 순수 함수라 그대로 재사용하고,
`QuizSubmitRequest`는 이미 `null`(skipped)을 정식 값으로 받으므로 스키마도 재사용한다.

rate limit은 `checkRateLimit`을 `prefix: "hint"`로 재사용하되 LLM 호출이 아니니 넉넉하게
— 분당 60. 라운드당 최대 10회라 정상 사용자는 닿지 않는다.

## 3. 판정 — `lib/hint-policy.ts`

`.server.ts`가 아니라 순수 모듈. `cloudflare:workers`를 import하지 않으니 vitest에서
그대로 돌고, 이 기능에서 유일하게 "틀리면 티 안 나게 이상해지는" 로직이라 테스트가
실제로 필요한 부분이다.

입력: 행동 신호(번복·재방문) + 서버가 방금 계산한 성적(답한 수, 맞힌 수,
**이 문항 카테고리에서 이미 틀린 수**) + 난이도. 출력은 체류 임계값(ms) —
`nudgeThresholdMs(input)`.

초안 규칙:

- 기본 임계 35초
- 같은 카테고리에서 이미 틀린 적 있음 → 20초로 당김
- 3문항 이상 답했고 정답률 80% 이상 → 60초로 늦춤 (잘 가는 사람 방해 금지)
- `hard` → +10초
- 선택을 3번 이상 갈아치움 → -10초
- 재방문 → 즉시 (돌아왔다는 건 확실히 막혔다는 뜻)
- 어떤 조합이든 8초(`MIN_NUDGE_AT_MS`) 밑으로는 내려가지 않는다 — 문항을 읽을 시간은 준다

숫자는 전부 추측이다. 다만 PostHog에 `question_viewed`가 index·재방문 여부와 함께
쌓이고 있어 **실제 체류 분포를 보고 조정할 재료가 있다.**

### 유출 재점검

응답에서 과거 정답률에 영향받는 건 `nudge_at_ms` 하나뿐이고, 그마저 on/off가 아니라
**임계값 이동**이다. "뱃지가 빨리 떴다 = 아까 틀렸다"를 역추론하려면 체류 시간을
통제하며 여러 번 재현해야 하는데, 앞 답을 고치면 화면이 그 문항으로 돌아가 관측이
끊긴다.

**지켜야 할 선: 정답률이 `nudge_at_ms`를 즉시 뒤집게 만들지 않는다.** 임계값 조정 이상은
하지 않는다.

## 4. UI — `app/play/hint-buddy.tsx`

우측 하단 fixed. 상태는 `idle` → `available` → `open` 셋뿐이고 문항이 바뀌면 리셋.

요청은 **방문당 한 번**. 서버가 돌려줄 수 있는 가장 이른 시점(`MIN_NUDGE_AT_MS`,
8초)에 한 번 쏘고, 사용자가 그전에 탭하면 그 자리에서 쏘되 예약된 자동 요청은 취소한다.
**방문마다 새로 묻고 캐시하지 않는다** — 임계값은 문항의 성질이 아니라 그 순간 사람의
상황이라, 첫 방문의 35초를 재방문에 재사용하면 "되돌아왔다 = 확실히 막혔다"는 신호가
통째로 묻힌다.

실패하면 조용히 `idle`로 남는다. 에러 토스트를 띄우지 않는다 — Upstash·PostHog·Anthropic을
전부 "미설정이면 no-op"으로 두는 것과 같은 결이고, 부가 기능이 본 흐름을 방해하면 안 된다.

빠뜨리면 안 되는 두 가지:

- **`prefers-reduced-motion`이면 움직임을 끄고 뱃지 점만 남긴다.** 구석에서 계속
  꼼지락거리는 요소는 전정 감각이 예민한 사용자에게 실제로 괴롭다.
- **캐릭터는 `<button aria-label="힌트">`이고 뱃지 상태를 label에 반영한다**("힌트 있음").
  애니메이션은 스크린리더에 존재하지 않는 신호라, 그대로 두면 그 사용자에게 이 기능은
  통째로 없는 것과 같다.

마스코트 이모지는 이 설계와 독립이다. `feat/cat-persona`(🍘→🐱)는 문자열 교체뿐이고
이미지 에셋이 없으므로, 지금 이모지로 짓고 나중에 한 글자만 바뀐다.

## 5. 의도적으로 안 하는 것

**힌트 사용 횟수를 결과나 공유 카드에 남기지 않는다.** "힌트 3번 씀"이 결과에 뜨는
순간 `docs/DECISIONS.md`가 지운 학습 압박이 뒷문으로 돌아온다.

부수 효과로 **D1 스키마가 안 바뀌므로 마이그레이션 선행 PR이 필요 없다.**

## 검증

- `lib/hint-policy.ts` 단위 테스트 — 임계값 경계, 잘 가는 사람 억제, 재방문 즉시
- `scripts/check-questions.ts`에 **힌트 유출 린트**: 힌트가 정답 보기 텍스트를 그대로
  포함하면 실패. `lint-question-prose.ts` 옆에 붙는 성격이고, 이게 있어야 129개를
  기계로 초안 잡아도 안심된다.
- e2e 하나 — 캐릭터 탭 → 힌트 노출

## 순서 (PR 4개)

1. 스키마 `hint` optional + `hint_html` 번들 + 유출 린트 + 문항 몇 개 수동 작성
2. `/api/quiz/hint` + `lib/hint-policy.ts` + 테스트
3. `HintBuddy` UI
4. 129문항 힌트 일괄 생성 — `quiz-author` 파이프라인 확장, 검수 부하 때문에 카테고리별로 쪼개서

1~3은 힌트가 몇 개만 있어도 동작하니 순서대로 머지 가능하고, 4가 늦어져도 이미 배포된
기능이 깨지지 않는다.

## 열어둔 것

지금 설계는 "지나온 답변"을 감도 조절에만 쓴다. 그 이상(예: 앞에서 클로저를 틀렸으니
지금 비동기 문항에서 그 얘기를 꺼낸다)은 힌트 문장이 문맥에 따라 달라져야 하는 것이라
YAML 고정과 충돌한다. **현재 결정대로면 그 층은 없다.**
